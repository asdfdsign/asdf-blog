## 블로그와 맞출 것 (선택이 아니라 요구)

- **다크 모드**: 블로그는 `<html data-theme="dark|light">` 로 전환하고 `localStorage` 키 `theme` 에 저장한다. 시스템 설정 `prefers-color-scheme` 이 기본값. 앱은 같은 키를 읽어 같은 테마로 뜨게 한다 (head 에서 동기 실행해 플래시 방지). 앱 자체 토글은 두어도 되고 안 두어도 된다 — 계획에서 정하라.
- **색 변수**: 블로그의 팔레트를 그대로 가져다 쓴다. 라이트 `--bg #fbfaf9 --bg-elevated #f2efec --text #1c1917 --text-muted #6b6461 --border #e4dfdb --accent #c8202a --accent-soft #fbe9ea --accent-contrast #fff`, 다크 `--bg #141214 --bg-elevated #1e1b1d --text #ece7e4 --text-muted #a39a96 --border #2c2729 --accent #ff6b6e --accent-soft #3a1e20 --accent-contrast #141214`. 색은 전부 CSS 변수로, 하드코딩 금지. 포인트 컬러는 선택·강조에만.
- **타이포**: 시스템 산세리프 스택(Pretendard 우선). 숫자는 `font-variant-numeric: tabular-nums`.

## spec.md 에 반드시 담을 것

1. **한 줄 소개** — 블로그 카드에 그대로 쓸 제목과 설명(한국어, 설명은 40자 안팎).
2. **게임 범위** — "미니"의 정의. 4×4(2×2 박스)·6×6(2×3 박스)을 기본으로 하고 9×9는 넣을지 말지 근거와 함께 정한다. 난이도(빈칸 수), 힌트/지우기/메모(연필 표시) 중 무엇을 1차에 넣고 무엇을 뺄지 명시.
3. **퍼즐 생성 방식** — 매번 새 판이어야 한다. 백트래킹으로 완성판 생성 → 유일해를 유지하며 칸 제거하는 방식을 권한다. 유일해 검증을 어떻게 할지, 6×6 에서 성능이 괜찮은지(브라우저 메인 스레드에서 100ms 안), 실패 시 대안을 적는다.
4. **UI 흐름** — 화면 구성(상단: 크기·난이도·새 게임, 가운데: 보드, 아래: 숫자 패드·지우기·힌트·타이머), 입력 방식(칸 탭 → 숫자 패드 / 키보드 숫자·화살표·Backspace 둘 다), 오류 표시(같은 행·열·박스 충돌은 즉시 표시), 완성 시 축하 상태. 모바일과 데스크톱 레이아웃 차이.
5. **상태 저장** — 진행 중인 판을 `localStorage` 에 저장해 새로고침해도 이어지게 할지. 키 이름은 `sudoku:` 접두사로 블로그 키와 충돌하지 않게.
6. **접근성** — 보드는 `role="grid"`, 칸은 버튼, 선택 칸 `aria-selected`, 충돌 칸은 색만이 아니라 텍스트/아이콘으로도 구분, 키보드만으로 완주 가능.
7. **파일 구조** — `apps/sudoku/` 아래 `index.html`, `style.css`, `app.js`(UI), `sudoku.js`(생성·검증, DOM 의존 없는 순수 함수), 필요하면 `theme.js`. 각 파일이 하는 일 한 줄씩.
8. **`sudoku.js` 공개 함수 목록** — 이름·입력·출력. Review 단계에서 이 함수들을 콘솔/테스트 페이지로 검증할 수 있게. 테스트 페이지 `apps/sudoku/test.html` 을 둘지 결정.
9. **검증 체크리스트** — Review 서브에이전트가 브라우저에서 확인할 항목. 최소: 새 게임 20번 연속 생성 시 전부 유일해, 375px 가로 스크롤 없음, 라이트/다크 대비, 키보드만으로 한 판 완주, 새로고침 후 이어하기, 콘솔 에러 없음, iframe(폭 360px) 안에서 보드 전체가 보임.
10. **안 하는 것** — 1차에서 뺀 기능을 명시.
