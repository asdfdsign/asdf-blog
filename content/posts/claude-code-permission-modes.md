클로드 코드를 켜면 화면 아래에 "기본", "편집 자동 수락", "자동" 같은 모드가 보입니다. 처음엔 뭐가 다른지 몰라 그냥 두고 썼는데, 블로그 작업을 두 프로젝트 하면서 세 가지를 다 겪어 봤습니다. 이 글은 그 차이를 처음 보는 사람 눈높이로 정리한 것입니다.

## 한 문장으로

> 권한 모드는 **"어디까지 묻지 않고 해도 되는가"** 의 단계입니다.

직원에게 결재 권한을 얼마나 주느냐와 같습니다. 모든 걸 사장이 결재하는 회사도 있고, 문서 작성은 알아서 하되 돈 쓰는 건 결재받는 회사도 있고, 웬만한 건 알아서 하되 위험한 것만 멈추는 회사도 있습니다.

## 모드별로

**기본(default)** — 파일을 고치거나 명령을 실행할 때마다 **매번 묻습니다.** 승인 창이 뜨고 사람이 누릅니다. 처음 보는 저장소나 남의 코드를 다룰 때 맞는 모드입니다. 무엇을 하는지 하나하나 보게 되니까요.

**편집 자동 수락(acceptEdits)** — **파일 편집은 묻지 않습니다.** 글을 고치고, 코드를 쓰고, 새 파일을 만드는 건 알아서 합니다. 하지만 **명령 실행은 여전히 묻습니다.** `git push`, `python script.py` 같은 것은 승인 창이 뜹니다. "문서 작성은 알아서 하되, 바깥에 영향 주는 건 결재받아라"입니다.

**자동(auto)** — 편집도 명령도 **대부분 묻지 않습니다.** 대신 뒤에서 **분류기가 감시**하다가 위험해 보이는 것만 멈추고 묻습니다. "웬만한 건 알아서 하되, 회사 이름으로 계약서 쓰는 건 멈춰라"입니다.

**계획(plan)** — 읽기만 합니다. 아무것도 고치지 않고 계획만 세웁니다. 큰 작업을 시작하기 전에 "어떻게 할 건지 먼저 보자" 할 때 씁니다.

**전부 우회(bypassPermissions)** — 감시도 없이 전부 실행합니다. 격리된 환경(예: 클라우드 루틴처럼 매번 새로 만드는 컴퓨터)이 아니면 쓰지 않는 게 좋습니다.

## 편집 자동 수락과 자동, 실제로 뭐가 다른가

둘 다 "파일 고치는 건 안 묻는다"는 점은 같습니다. 갈리는 건 **명령 실행**입니다.

편집 자동 수락에서 클로드가 `git push`를 실행하려 하면 승인 창이 뜹니다. 파일은 자유롭게 고쳐도, 그 파일을 실행하거나 바깥으로 내보내는 순간엔 사람이 봅니다. 안전한 대신, 명령을 수십 번 쓰는 날에는 계속 클릭해야 합니다.

자동 모드에서는 그 명령들도 그냥 실행됩니다. 이 블로그를 만든 세션이 실제로 자동 모드였습니다. 하루에 `git push`, `gh repo create`, `python` 스크립트, 브라우저 확인을 수십 번 했는데, 승인 창 없이 이어졌습니다. 그 대신 안전장치가 두 겹 있습니다.

### 1겹 — 거부 규칙

설정 파일에 "이건 절대 안 됨"을 적어 둘 수 있습니다. 예를 들면 이런 것들입니다.

```
rm -rf*
git push --force*
git reset --hard*
npm install*
```

**모드와 상관없이 무조건 막힙니다.** 첫 블로그에서 이걸 시험했습니다. 자동 모드로 돌면서 `rm -rf /tmp/없는폴더`를 실행해 봤더니 이런 메시지와 함께 차단됐습니다.

```
Permission to use Bash with command rm -rf /tmp/this-folder-does-not-exist has been denied.
```

없는 폴더라 실행돼도 아무 일 없는 명령인데도 막혔습니다. **대상을 보지 않고 명령의 모양만 보고 판단**한다는 뜻입니다. 그게 의도한 동작입니다.

### 2겹 — 자동 승인 분류기

규칙에 없어도 "이건 위험하다"고 판단하면 멈추고 묻습니다. 같은 세션에서 두 번 걸렸습니다.

- 클로드가 권한 설정 파일을 통째로 덮어쓰려 했을 때
- 클로드가 어떤 도구를 스스로 허용 목록에 넣으려 했을 때

둘 다 "클로드가 자기 권한을 스스로 넓히는" 모양이라 막혔습니다. 이 층은 파일이 아니라 모델 쪽에 있어서 **클로드가 편집할 수 없습니다.** 규칙 파일은 클로드가 고칠 수 있지만, 분류기는 못 고칩니다. 그래서 자동 모드가 "다 풀어 준 것"과는 다릅니다.

## 어느 걸 언제 쓰나

- **처음 보는 저장소, 남의 코드** → 기본. 뭘 하는지 하나하나 봐야 합니다.
- **내 프로젝트에서 글이나 코드를 많이 고치는 날** → 편집 자동 수락. 파일 편집은 git으로 되돌릴 수 있으니 안 물어도 되고, 명령은 한 번 더 보고 싶을 때.
- **편집 + 빌드 + 배포 + 확인을 수십 번 반복하는 날** → 자동. 대신 거부 규칙을 먼저 채워 두고 씁니다.
- **뭘 할지 감이 안 올 때** → 계획. 읽기만 하니 아무것도 안 망가집니다.

## 방어 장치를 시험하는 법

규칙을 넣었으면 실제로 걸리는지 확인해야 합니다. 그런데 "프로젝트 폴더를 지워 봐"처럼 시험하면, 규칙이 안 걸렸을 때 진짜로 지워집니다. 첫 블로그에서 실제로 그 요청이 있었고, 클로드가 거절했습니다.

> 방어 장치를 시험할 때는, 실패해도 안전한 명령을 써야 한다.

같은 모양이되 대상이 무해한 것으로 시험합니다.

- `rm -rf /tmp/없는폴더` — 모양은 `rm -rf`, 대상은 없는 폴더
- `git push --force` — 로컬과 원격이 같은 커밋일 때. 실행돼도 아무 변화 없음
- `npm install lodash --dry-run` — `--dry-run`이라 실제로 설치 안 됨

셋 다 규칙에 걸리는지는 그대로 드러나고, 안 걸려도 아무 일이 없습니다.

## 기억해 둘 것 하나

모드는 **"얼마나 묻느냐"** 를 바꾸는 것이지 **"무엇을 할 수 있느냐"** 를 바꾸는 게 아닙니다. 자동 모드라고 거부 규칙이 풀리지 않고, 기본 모드라고 못 하는 게 생기지 않습니다.

그래서 진짜 금지선은 모드가 아니라 **거부 규칙**에 적어 둡니다. 모드는 그날 작업에 따라 바꾸지만, 규칙은 저장소를 따라다니니까요.

## 오늘의 한 줄 정리

- 권한 모드 = 어디까지 묻지 않고 해도 되는가. 기본 → 편집 자동 수락 → 자동 순으로 덜 묻는다.
- 편집 자동 수락은 파일만, 자동은 명령까지. 차이는 명령 실행이다.
- 자동 모드에도 안전장치가 두 겹 — 거부 규칙(내가 적음)과 분류기(클로드가 못 고침).
- 금지선은 모드가 아니라 거부 규칙에 적는다.
- 방어 장치는 실패해도 안전한 명령으로 시험한다.
