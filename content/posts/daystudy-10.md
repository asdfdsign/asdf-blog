## 완성된 링크 안쪽까지 훑는 정규식

마크다운 파서(`js/markdown.js`)는 `**굵게**`, `*기울임*`, `[링크](주소)` 같은 문법을 정규식으로 하나씩 치환합니다. 리뷰 전까지는 순서가 코드 → 이미지 → 링크 → 굵게 → 기울임이었습니다.

문제는 링크를 완성해 놓고 나서, 그 뒤에 기울임 정규식이 글 전체를 다시 훑는다는 점입니다. 이런 글을 쓰면:

```md
[배포 노트](https://example.com/*release*)
```

링크를 먼저 만들면 `<a href="https://example.com/*release*">배포 노트</a>` 가 됩니다. 그런데 기울임 정규식은 "링크인지 아닌지"를 모르고 그냥 `*...*` 모양을 찾습니다. `href` 속성 안의 `*release*` 도 똑같이 걸려서 이렇게 바뀝니다.

```html
<a href="https://example.com/<em>release</em>">배포 노트</a>
```

주소 안에 태그가 끼어들면서 링크가 엉뚱한 곳으로 깨집니다. 지금까지 이 블로그 글에는 `*`가 든 주소가 없어서 드러나지 않았던 버그입니다.

고친 방법은 "이미 만든 조각은 다시 건드리지 못하게 치워 두기"입니다. 코드·이미지·링크를 만들 때마다 결과를 배열에 담아 두고, 글자 자리에는 자리표시자(예: `\0 3 \0`)만 남깁니다. 기울임·굵게 정규식은 이 자리표시자만 보기 때문에, 이미 완성된 HTML 속성 안쪽으로는 들어갈 길이 없습니다.

```js
const parts = [];
const hold = html => {
  parts.push(html);
  return `\u0000${parts.length - 1}\u0000`;
};

s = s.replace(/\[([^\]]+)\]\(([^)]+)\)/g, (_, label, href) =>
  hold(`<a href="${href}">${renderEmphasis(label)}</a>`)
);
```

링크 라벨 안에는 기울임을 쓰고 싶을 때가 있어서(`[**중요**한 글](...)`), 라벨만 먼저 `renderEmphasis`로 돌리고 그 결과를 통째로 치워 둡니다. 맨 끝에서 자리표시자를 실제 HTML로 되돌리는데, 이 복원도 한 번이 아니라 "더 남은 자리표시자가 없을 때까지" 반복합니다 — 치워 둔 조각 안에 또 다른 자리표시자가 있을 수 있기 때문입니다.

## 느린 응답이 새 화면을 덮어쓰는 문제

두 번째는 라우터(`js/app.js`)입니다. 주소(`#/...`)가 바뀌면 `route()`가 `fetch`로 글 목록이나 본문을 가져와 화면을 바꿉니다. `fetch`는 시간이 걸리고, 그 사이에 사용자가 또 다른 주소로 넘어갈 수 있습니다.

네트워크 응답은 보낸 순서대로 돌아온다는 보장이 없습니다. A 글을 열고 바로 B 글로 넘어갔는데 A의 응답이 B보다 늦게 도착하면 — 고치기 전 코드는 그냥 "응답이 왔으니" 화면을 바꿔서, 주소창은 B인데 화면은 A로 덮입니다.

고친 방법은 라우팅마다 번호(세대)를 매기는 것입니다. `route()`가 호출될 때마다 번호를 하나 올리고, 화면을 실제로 바꾸기 직전에 "내 번호가 아직 최신인가"를 확인합니다.

```js
let routeVersion = 0;
const stale = version => version !== routeVersion;

async function route() {
  const version = ++routeVersion;
  const posts = await loadIndex();
  if (stale(version)) return; // 그사이 더 새로운 라우팅이 시작됐다
  show(view, title, version);
}
```

늦게 도착한 A의 응답은 자기 번호가 낡았다는 걸 확인하고 조용히 멈춥니다. 데이터를 못 가져오게 막는 게 아니라, **화면에 반영하는 마지막 순간에만** 최신 여부를 검사하는 것이 핵심입니다.

같은 리뷰에서 캐시 쪽도 하나 고쳤습니다. `loadIndex()`는 `posts.json`을 한 번만 받아 캐시하는 함수인데, 첫 로딩이 끝나기 전에 여러 화면이 동시에 부르면(목록과 카테고리 바가 같은 타이밍에 부르는 식) 캐시가 비어 있어 매번 새 `fetch`가 뜹니다. "끝난 결과"뿐 아니라 "진행 중인 약속(Promise)"도 같이 들고 있다가 돌려주면, 두 번째 호출은 새 요청 없이 첫 번째가 끝나길 같이 기다립니다.

## 확인이 필요한 부분

- 코덱스 리뷰가 찾은 10건(높음 1·중간 4·낮음 5) 중 여기서 다룬 건 두 건뿐입니다. 나머지(URL 인코딩 통일, 저장된 테마 값 검증, 화면 전환 후 포커스 이동 등)는 커밋 메시지에만 있어 분량상 뺐습니다 — 전체 내용은 `codex-review.md`에 있습니다.
- 스도쿠·포모도로 두 미니 웹앱을 만든 과정(Plan→Build→Review→Embed, 서브에이전트 셋)은 이번 글에서 다루지 않았습니다. 다음 Daystudy에서 다룰지 정해야 합니다.
- `--rest` 같은 웹앱 전용 색 변수의 대비 4.5:1 실측값은 커밋 메시지에 수치가 없어 확인하지 못했습니다.

## 오늘의 한 줄 정리

- 정규식을 여러 번 겹쳐 돌릴 때는 "이미 완성된 조각을 다시 훑지 않는다"가 중요합니다 — 자리표시자로 치워 두면 지켜집니다.
- 비동기 작업은 끝나는 순서가 시작한 순서와 다를 수 있습니다. 화면을 바꾸는 마지막 순간에 "내가 아직 최신인가"를 확인하면 늦게 온 응답이 새 화면을 덮지 못합니다.
- 캐시는 "끝난 값"뿐 아니라 "진행 중인 약속"도 같이 들고 있어야 중복 요청을 막습니다.
