이 블로그가 글만 쓰는 곳에서 미니 웹앱도 만드는 포트폴리오로 바뀌었습니다. `CLAUDE.md`가 통째로 교체되면서 "Plan → Build → Review → Embed"라는 작업 사이클이 생겼고, 그 사이클로 스도쿠와 포모도로 타이머 두 앱을 실제로 만들었습니다. 오늘은 그 과정에서 **왜 한 클로드가 다 하지 않고 서브에이전트를 나누는지**를 정리합니다.

## 지침 파일로 범위를 자른다

새 규칙은 단계마다 전담 서브에이전트를 만들고, 그 에이전트에게는 전용 지침 `.md` 파일을 하나 건넵니다. Plan 에이전트는 계획만 짜서 `spec.md`로 남기고, Build 에이전트는 그 계획대로 `/apps/{이름}/` 폴더 **안에서만** 코드를 씁니다. 실제로 두 앱 모두 `apps/{이름}/agent/plan.md`, `build.md`, `review.md` 세 파일이 함께 커밋됐습니다 — 각 에이전트에게 무엇을, 어디까지 해도 되는지 적어 둔 쪽지입니다.

```
apps/pomodoro/
  agent/plan.md    ← Plan 에이전트에게 준 지침
  agent/build.md   ← Build 에이전트에게 준 지침
  agent/review.md  ← Review 에이전트에게 준 지침
  spec.md          ← Plan 의 산출물
  review.md         ← Review 의 산출물
```

지침 파일이 있으면 "이 에이전트가 왜 이 파일만 건드렸는지"가 나중에도 커밋 기록으로 남습니다. 자유롭게 다 하게 두는 것보다, 무엇을 하지 말아야 하는지를 먼저 적어 주는 쪽이 결과를 예측 가능하게 만든다는 걸 알게 됐습니다.

## Build 와 Review 를 분리하는 이유

CLAUDE.md 는 "Build 서브에이전트와 Review 서브에이전트는 반드시 분리한다"고 못 박고 있습니다. 같은 에이전트가 자기가 짠 코드를 스스로 검토하면, 자기가 놓친 것을 또 놓칠 가능성이 크기 때문일 겁니다. 포모도로 앱의 `review.md`를 보면 이게 실제로 효과가 있었습니다.

> 통과 46 / 46 (spec 12절 항목 기준), 수정 2건(경미)

두 건 중 하나는 CSS 우선순위 문제였습니다. 타이머가 0초에 도달하면 링이 `opacity 0`으로 사라져야 하는데, 규칙 순서가 잘못돼 있어서 안 사라졌습니다.

> 수정: 규칙을 펄스 규칙 **뒤로** 옮기고 선택자를 `.ring__progress.is-empty, .timer.is-ending .ring__progress.is-empty`로 늘렸다.

다른 하나는 코드 자체는 동작하지만 품질이 떨어지는 문제였습니다. 1초마다 화면 숫자를 갱신하는데, 값이 같을 때도 매번 `textContent`를 새로 대입하고 있었습니다. 눈에는 안 보이지만 불필요한 리렌더가 계속 일어나는 셈입니다.

> 수정: 현재 `textContent`와 다를 때만 대입(같은 방식의 두 줄 가드).

둘 다 Build 에이전트가 "동작은 한다"고 넘긴 코드였고, Review 에이전트가 따로 체크리스트를 들고 실제로 화면을 조작해 보면서 잡아낸 것입니다. 검토가 작성자와 분리돼 있었기 때문에 가능했던 일이라고 봅니다.

## 시간을 테스트할 수 있게 짜기

포모도로 타이머는 "지금 몇 초 남았는가"를 계속 계산해야 하는데, 이 계산이 `apps/pomodoro/timer.js`에 순수 함수로 따로 빠져 있습니다.

```javascript
function remaining(state, now) {
  var r;
  if (state.status === 'running') r = state.endAt - now;
  else if (state.status === 'paused') r = state.remainingMs;
  else r = state.durationMs;
  return Math.max(0, Math.min(state.durationMs, r));
}
```

시계를 직접 읽지 않고 `now`를 인자로 받습니다. 그 덕분에 테스트 파일(`test.html`)이 실제로 1분을 기다리지 않고도 "25분 뒤"나 "새로고침 직후" 같은 상황을 가짜 시각 값 하나로 흉내 낼 수 있습니다. 포모도로 쪽 테스트가 119개나 되는데, 함수가 시계에 묶여 있었다면 이 정도 개수를 빠르게 돌리기 어려웠을 겁니다. 스도쿠 쪽도 같은 이유로 생성·검증 로직이 DOM과 분리된 `sudoku.js`에 따로 있고, 여기 테스트는 56개입니다.

## 규칙도 뒤늦게 보완했다

두 앱을 만들고 나서야 CLAUDE.md 에 "웹앱 규칙" 두 개가 추가됐습니다. 블로그 색상 변수를 앱에 그대로 복사해서 쓸 것, 그리고 조작법을 상시 설명 없이 접이식 `<details>` 하나로만 둘 것. 이미 만든 두 앱에는 이 규칙이 없었기 때문에, 규칙을 추가한 커밋이 스도쿠와 포모도로 양쪽에 「사용법」 접이식을 소급 적용했습니다. 사이클을 다 정하고 시작한 게 아니라, 만들어 보면서 빠진 규칙을 채워 넣은 셈입니다.

## 확인이 필요한 부분

- Plan·Build·Review 세 에이전트를 실제로 부른 순서와 대화 내용은 커밋에 안 남아 있어, 각 단계가 정말 별도 세션이었는지는 확인이 필요합니다.
- 웹앱 규칙(팔레트·사용법)을 나중에 추가하기로 한 이유 — 처음부터 정하지 않은 게 의도적인지, 만들면서 빠진 걸 알게 된 건지.
- 대비 4.5:1을 앱에서 실제로 어떻게 쟀는지(도구·방법)는 review.md 안에 더 있을 수 있어 필요하면 원문을 봐야 합니다.

## 오늘의 한 줄 정리

- 서브에이전트에게는 전용 지침 파일로 범위를 미리 잘라 준다 — `spec.md`·`review.md`처럼 산출물도 파일로 남긴다.
- Build 와 Review 를 분리하면 작성자가 놓친 문제(CSS 우선순위, 불필요한 리렌더)를 검토자가 잡아낸다.
- 시간처럼 바뀌는 값은 함수 인자로 받게 짜면, 실제로 기다리지 않고도 많은 경우를 테스트할 수 있다.
- 규칙은 처음에 다 정해 놓지 않아도 된다 — 만들어 보고 빠진 걸 CLAUDE.md 에 보완한 뒤 이미 만든 것에도 소급 적용하면 된다.
