지난 커밋에서 코덱스에게 블로그 본체 코드를 처음으로 리뷰받았습니다. 지금까지 review.md 는 늘 웹앱 쪽이었고, 글을 HTML 로 바꿔 화면에 꽂아 넣는 본체 코드(`js/app.js`)는 리뷰를 받은 적이 없었습니다. 열 건이 나왔는데, 그중 가장 이해하기 어려웠던 하나가 **비동기 요청의 경쟁 상태(race condition)** 였습니다.

## 무슨 상황이었나

이 블로그는 주소가 `#/post/글이름` 처럼 해시로 바뀌면 그에 맞는 글을 fetch 로 받아와 화면에 그립니다. 코드는 대략 이런 모양이었습니다.

```js
window.addEventListener('hashchange', route);

async function route() {
  const hash = location.hash;
  // ... 해시를 분석해서 ...
  const post = await loadPost(slug); // 네트워크 요청, 시간이 걸린다
  show(post); // 화면을 바꾼다
}
```

평소에는 문제가 없습니다. 그런데 사람이 글 A를 눌렀다가 — 로딩이 끝나기 전에 — 마음을 바꿔 글 B를 누르면 어떻게 될까요. `route()` 가 두 번 실행되면서 **네트워크 요청도 두 번** 나갑니다. 문제는 둘 중 **어느 쪽이 먼저 끝나는지 보장이 없다**는 것입니다. 글 B가 더 가벼워서 먼저 끝나 화면에 떴는데, 뒤늦게 글 A의 요청이 끝나면 — 아무도 막지 않았으니 — 화면이 다시 **글 A로 덮입니다.** 주소창은 B를 보여주는데 화면은 A인, 둘이 어긋난 상태가 됩니다.

## 왜 '당연히 순서대로'가 아닌가

자바스크립트 코드 한 줄 한 줄은 순서대로 실행되지만, `fetch` 같은 비동기 작업은 코드 밖(네트워크)에 나갔다가 **끝나는 순서를 코드가 정할 수 없는 채로** 돌아옵니다. 식당에서 주문 두 개를 연달아 넣었는데 주방 사정에 따라 나중 주문이 먼저 나올 수 있는 것과 같습니다. 코드를 작성한 순서와 실제로 끝나는 순서는 다른 이야기입니다. `await` 는 "기다렸다가 다음 줄로 간다"는 뜻일 뿐, "먼저 시작한 게 먼저 끝난다"는 뜻이 아닙니다.

## 고친 방법 — 세대 번호

고친 코드는 라우팅이 시작될 때마다 번호를 하나씩 올립니다. 그리고 화면을 실제로 바꾸는 단계에서, **지금 내가 들고 있는 번호가 아직도 최신인지** 확인합니다.

```js
let routeVersion = 0;
const stale = version => version !== routeVersion;

function show(node, title, version) {
  if (stale(version)) return; // 이미 더 최신 라우팅이 지나갔다 — 그만둔다
  app.replaceChildren(node);
  document.title = title;
}

async function route() {
  const version = ++routeVersion; // 이번 라우팅의 번호를 받는다
  const post = await loadPost(slug);
  show(post, title, version); // 화면을 바꿀 땐 그 번호를 들고 간다
}
```

글 A가 요청을 보낼 때 번호 1을 받고, 글 B가 보낼 때 번호 2를 받습니다. `routeVersion` 자체는 그 시점에 바로 2가 됩니다. 나중에 글 A의 요청이 돌아와 `show` 를 부르려 해도, 자기가 들고 온 번호(1)가 지금 번호(2)와 다르니 `stale(1)` 이 참이 되어 **화면을 건드리지 않고 조용히 멈춥니다.** 늦게 도착한 결과를 버리는 게 아니라, "화면에 반영하는 마지막 한 걸음"만 막는 것이 핵심입니다 — 번호 자체는 가볍게 비교만 하면 되니 복잡한 잠금 장치가 필요 없습니다.

검증은 느린 네트워크 상황을 일부러 만들어(로딩 중에 해시를 빠르게 바꿔가며) 주소와 화면이 끝까지 일치하는지, 그리고 `posts.json` 요청이 중복으로 나가지 않는지 확인했습니다.

## 확인이 필요한 부분

- 실제 모바일 네트워크(느린 3G 등)에서도 같은 방식으로 재현해서 확인했는지는 커밋 메시지에 없어 알 수 없습니다. 로컬 테스트만으로 충분한지 사람이 판단이 필요합니다.
- 세대 번호가 전역 변수 하나(`routeVersion`)에 의존하는데, 이 블로그처럼 화면이 하나뿐인 구조를 벗어나 화면을 여러 개 동시에 띄우는 구조로 커지면 이 방식이 그대로 맞는지는 다시 봐야 합니다.
- 코덱스가 찾은 나머지 아홉 건(마크다운 링크 안의 URL이 망가지는 문제, 테마 값 검증 등)도 같은 커밋에 함께 들어갔습니다. 이 글은 그중 하나만 다뤘으니, 나머지는 필요하면 `codex-review.md` 를 보고 따로 정리하면 좋겠습니다.

## 오늘의 한 줄 정리

- 비동기 요청은 시작한 순서대로 끝난다는 보장이 없다 — 늦게 시작한 쪽이 먼저 끝날 수 있다.
- 화면을 실제로 바꾸는 마지막 단계에, "나는 아직 최신 요청인가"를 번호로 확인하는 가드를 둔다.
- 번호가 다르면(= 더 최신 라우팅이 이미 지나갔으면) 늦게 온 결과는 화면에 반영하지 않고 버린다.
