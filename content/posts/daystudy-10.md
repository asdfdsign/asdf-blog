지난 글(Daystudy #9) 이후 블로그 본체가 처음으로 코드 리뷰를 받았습니다. 웹앱 두 개(스도쿠, 포모도로)를 먼저 만들고, 그 사이클이 익숙해진 뒤에야 "그런데 블로그 자체는 한 번도 리뷰 안 받았네" 하고 돌아본 것입니다. 리뷰에서 나온 열 가지 중 하나가 특히 낯설었습니다 — **경쟁 상태(race condition)**. 오늘은 이것 하나만 뜯어봅니다.

## 어떤 문제였나

이 블로그는 주소(해시)가 바뀔 때마다 `content/posts.json`을 다시 읽어 화면을 그립니다. `fetch`는 비동기라서, "요청을 보낸 순서"와 "응답이 돌아오는 순서"가 항상 같지는 않습니다.

예를 들어 사용자가 글 A를 열었다가 바로 글 B로 넘어가면, A를 위한 요청과 B를 위한 요청이 거의 동시에 날아갑니다. 그런데 네트워크 상태에 따라 **A의 응답이 B보다 늦게** 도착할 수 있습니다. 이때 "응답이 왔으니 화면을 그린다"는 코드만 있으면, 늦게 도착한 A가 방금 그려진 B 화면을 덮어씌웁니다. 주소창은 B인데 화면은 A — 눈으로 보면 "새로고침해야 맞는 글이 나오는" 버그입니다.

## 왜 생기는가 — 순서를 보장해 주는 게 없다

자바스크립트는 `fetch` 하나를 보내고 바로 다음 줄로 넘어갑니다. 응답이 "언제" 돌아올지는 자바스크립트가 아니라 네트워크가 정합니다.

```js
// 이렇게만 쓰면 늦게 온 응답이 그냥 이긴다
async function route() {
  const hash = location.hash;
  const data = await fetch(url).then(r => r.json());
  render(data); // 이 줄이 실행될 때 주소가 이미 바뀌어 있을 수 있다
}
```

달리기 시합에서 늦게 출발한 선수가 먼저 들어올 수 있는 것과 같습니다. 출발 순서(요청을 보낸 순서)가 도착 순서(응답을 그리는 순서)를 보장하지 않습니다.

## 어떻게 고쳤나 — 세대 번호

고친 방식은 "지금 몇 번째 이동인지"를 번호로 들고 다니다가, 번호가 지나간 결과는 화면에 반영하지 않는 것입니다. `js/app.js`에는 이렇게 되어 있습니다.

```js
let routeVersion = 0;
const stale = version => version !== routeVersion;

function show(node, title, version) {
  if (stale(version)) return; // 내 차례가 지났으면 아무것도 안 한다
  app.replaceChildren(node);
  // ...
}

async function route() {
  const version = ++routeVersion; // 이동마다 번호를 하나씩 올린다
  // ...
  return await renderList({ version }); // 번호를 들고 다닌다
}
```

주소가 바뀔 때마다 `routeVersion`을 하나 올리고, 그 순간의 번호를 `version`이라는 이름으로 데이터를 가져오는 함수들에 끝까지 들려 보냅니다. 응답이 돌아왔을 때 "내가 들고 있는 번호"와 "지금 전역 번호"가 다르면, 그사이 다른 이동이 있었다는 뜻이니 화면을 건드리지 않고 조용히 멈춥니다. 번호표를 뽑고 기다리다가, 내 번호가 이미 지난 차례면 그냥 자리를 뜨는 것과 같습니다.

## 왜 이 방식인가

대안으로 "이전 요청을 취소한다(AbortController)"도 있었을 텐데, 이 코드는 취소 대신 **결과를 무시**하는 쪽을 택했습니다. 요청 자체는 끝까지 가게 두고, 화면에 반영하는 마지막 순간에만 번호를 검사합니다. `syncNav`, `renderList`, `show`처럼 화면을 실제로 건드리는 지점마다 `stale(version)`을 넣어 둔 것도 그래서입니다 — 어디서 늦게 끝나든 마지막 문 앞에서 한 번 더 걸러지게 한 것입니다.

## 오늘의 한 줄 정리

- 비동기 코드에서는 "보낸 순서"와 "끝나는 순서"가 다를 수 있다. 느린 쪽이 나중에 화면을 덮어쓸 수 있다.
- 해결책 하나는 "세대 번호"를 들고 다니는 것 — 시작할 때 번호를 올리고, 화면을 그리기 직전에 그 번호가 아직 최신인지 확인한다.
- 지나간 번호의 결과는 취소하지 않고, 화면에 반영하는 마지막 지점에서 그냥 버린다.

## 확인이 필요한 부분

- 이번 글은 코덱스 리뷰가 찾은 열 가지 중 경쟁 상태 하나만 다뤘습니다. 나머지 아홉 가지(마크다운 파서의 링크·이미지 처리, 중복 fetch 캐싱, JSON 검증, URL 인코딩 통일 등)는 다른 날의 글감으로 남겨 둡니다.
- `AbortController`로 아예 이전 요청을 취소하는 방식과 지금의 "결과 무시" 방식을 실제로 비교해 보면 좋을 것 같습니다.
- 이 사이 두 웹앱(스도쿠, 포모도로)과 블로그 카테고리 구조(Daystudy/Essay/웹앱) 개편도 같이 있었는데, 분량상 별도 글로 미뤘습니다.
