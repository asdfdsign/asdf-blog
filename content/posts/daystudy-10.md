이 블로그의 마크다운 파서(`js/markdown.js`)는 직접 만든 것이라, 코드 리뷰(Codex)를 처음 받아 봤습니다. 치명적인 문제는 없었지만 하나가 눈에 걸렸습니다 — **링크를 만든 뒤에 돌아가는 정규식이 그 링크의 주소까지 다시 건드리고 있었습니다.** 지금까지 아무도 몰랐던 건 운이 좋았을 뿐이고, 실제로 재현해 보니 그대로 깨졌습니다.

## 문제: 강조 정규식이 완성된 href 안쪽까지 훑는다

파서는 원문을 차례로 처리합니다. 코드 → 이미지 → 링크 → 강조(굵게·기울임·취소선) 순서입니다. 문제는 각 단계가 **문자열 전체에 정규식을 다시 돌린다**는 점이었습니다. 링크를 `<a href="...">`로 바꿔 놓은 다음에도, 그 문자열 안에서 `*`로 둘러싸인 부분을 찾으면 강조 단계가 가차 없이 바꿔 버립니다.

이런 글을 쓰면:

```markdown
[배포 노트](https://example.com/*release*)
```

링크 자체는 멀쩡하게 만들어집니다.

```html
<a href="https://example.com/*release*">배포 노트</a>
```

그런데 바로 다음 단계인 강조 처리가 이 문자열을 다시 훑습니다. `*release*`를 "기울임 문법"으로 오해해서 이렇게 바꿔 버립니다.

```html
<a href="https://example.com/<em>release</em>">배포 노트</a>
```

href 안에 태그가 들어가 버렸으니 링크는 엉뚱한 주소로 갑니다. 다행히 따옴표는 이미 이스케이프돼 있어서 속성을 탈출하는 XSS는 아니었지만, **경고 없이 조용히 깨지는** 건 그것만으로 충분히 나쁩니다.

## 해법: 완성된 것은 즉시 자리표시자로 치운다

고치기 전 코드는 인라인 코드만 이런 식으로 보호하고 있었습니다. 백틱으로 감싼 코드를 뽑아서 번호가 붙은 자리표시자 문자열로 바꿔 두고, 다른 정규식이 다 지나간 다음 마지막에 원래 내용으로 복원하는 방식입니다. 이미 완성된 상품을 박스에 넣어 창고에 치워 두면, 뒤 공정이 아무리 매장을 휩쓸어도 박스 안까지는 건드리지 못하는 것과 같습니다.

이번 수정은 이 방식을 이미지·링크에도 그대로 적용했습니다.

```js
const parts = [];
const hold = (html) => {
  parts.push(html);
  return `\u0000${parts.length - 1}\u0000`;
};

// 이미지: 만들자마자 치운다
s = s.replace(IMAGE_RE, (_, alt, src, title) => {
  return hold(`<img src="${safeUrl(src)}" alt="${alt}">`);
});

// 링크도 마찬가지
s = s.replace(LINK_RE, (_, label, href) => {
  return hold(`<a href="${safeUrl(href)}">${label}</a>`);
});

// 맨 마지막에 남은 본문에만 강조를 적용
s = renderEmphasis(s);
```

다만 하나는 단순히 치우기만 하면 안 됐습니다. 링크 라벨(`[**중요**](...)`의 "중요" 부분)에는 강조가 걸려야 합니다. 그래서 라벨만 따로 `renderEmphasis()`로 먼저 처리한 뒤, href와 함께 통째로 자리표시자에 넣었습니다. **보호할 것(href)과 처리해야 할 것(라벨)을 같은 문자열 안에서 구분**해야 했던 셈입니다.

자리표시자를 쓰면 복원 순서도 신경 써야 합니다. 치워 둔 조각 안에 또 다른 자리표시자가 남아 있을 수 있어서(링크 라벨 안의 인라인 코드 같은 경우), 복원을 한 번이 아니라 **더 남은 자리표시자가 없을 때까지 반복**하도록 바꿨습니다. 다만 어떤 입력이 와도 무한히 돌지는 않게 반복 횟수에 상한(5회)을 두어 안전장치를 하나 더 마련했습니다.

## 왜 지금까지 안 드러났나

이 버그는 코드를 바꿔서 생긴 게 아니라 **처음부터 있었습니다.** 지금까지 쓴 글 중에 `*`나 `~~`가 들어간 URL이 하나도 없어서 드러나지 않았을 뿐입니다. 고치기 전 동작을 로컬 서버에서 직접 재현해 `href="https://example.com/<em>release</em>"`가 실제로 나오는 것을 확인한 뒤에야 안심하고 고쳤습니다. "지금 안 터진다"와 "버그가 없다"는 다른 말이라는 걸 다시 확인한 셈입니다.

## 확인이 필요한 부분

- 자리표시자 복원의 반복 상한(5회)이 실제로 넉넉한 값인지는 더 깊이 중첩된 입력으로 직접 시험해 보지 않았습니다.
- 이번 리뷰에서 함께 고친 `js/app.js`의 라우팅 경쟁 조건·`posts.json` 검증 등 나머지 9건은 분량상 이 글에서 다루지 않았습니다. 자세한 판정과 수정 내역은 저장소 루트의 `codex-review.md`에 있습니다.
- 커밋 메시지에는 "회귀 없음"이라고만 적혀 있어, 그 사이 추가된 포모도로·스도쿠 웹앱이나 카테고리 레이아웃 개편 같은 다른 작업은 이 글에 넣지 않았습니다. 다음 Daystudy에서 다룰 수 있습니다.

## 오늘의 한 줄 정리

- 정규식을 문자열 전체에 반복 적용하면, 이미 완성된 결과물(href 등)까지 다시 걸릴 수 있다.
- 완성된 조각은 자리표시자로 치워 두고, 맨 마지막에 복원한다 — 포장해서 창고에 넣는 것과 같다.
- 보호할 부분과 처리해야 할 부분이 같은 문자열에 섞여 있으면, 그 안에서 한 번 더 나눠 처리해야 한다.
- 자리표시자가 중첩될 수 있으면 복원도 한 번이 아니라 반복해야 하고, 반복에는 상한을 둬야 안전하다.
- 지금 글에 증상이 없다고 버그가 없는 건 아니다 — 실제로 재현해서 확인해야 한다.
