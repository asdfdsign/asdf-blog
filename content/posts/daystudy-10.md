이 블로그의 마크다운 파서(`js/markdown.js`)에 코드 리뷰를 받았습니다. 치명적인 문제는 없었지만, 한 가지는 "지금까지 안 터진 게 운이었다"는 종류의 버그였습니다. 링크 안에 `*`가 들어 있으면 주소가 조용히 망가지는 문제였습니다. 오늘은 그 버그가 왜 생겼고 어떻게 고쳤는지를 정리합니다.

## 문제: 링크를 만들었는데 안의 글자가 또 바뀐다

이런 링크를 쓴다고 해 봅시다.

```markdown
[배포 노트](https://example.com/*release*)
```

링크를 다 만든 뒤에, 결과 HTML이 이렇게 나옵니다.

```html
<a href="https://example.com/<em>release</em>">배포 노트</a>
```

href 안의 `*release*`가 기울임 태그로 바뀌어 있습니다. 당연히 이 주소로는 아무 데도 못 갑니다. 큰따옴표는 이미 이스케이프돼 있어서 XSS로 이어지지는 않지만, 경고 한 줄 없이 그냥 깨진 링크가 됩니다.

## 원인: 정규식은 자기가 아직 안 끝난 걸 모른다

이 파서는 인라인 문법(코드·이미지·링크·강조)을 정규식으로 순서대로 처리합니다. 고치기 전 순서는 `코드 → 이미지 → 링크 → 굵게 → 기울임 → 취소선`이었습니다.

문제는 "링크를 처리한다"는 게 원문 안의 `[라벨](주소)`를 찾아서 **그 자리에 완성된 `<a href="...">` 문자열을 박아 넣는 것**이라는 점입니다. 링크 정규식이 끝나면 문자열 전체에는 이제 막 만들어진 HTML 태그가 섞여 있습니다. 그런데 바로 다음 정규식(기울임)은 "지금 보고 있는 게 방금 만든 href 속성값인지"를 모릅니다. 그냥 문자열 전체를 처음부터 다시 훑습니다. `*release*`라는 모양만 보이면 기울임으로 바꿔 버립니다.

즉 각 정규식은 **독립적으로** 동작하는 것처럼 보이지만, 실제로는 이전 단계가 남긴 결과물 위에서 다음 단계가 또 돈다는 걸 깜빡하면 이런 자리에서 사고가 납니다.

## 해결: 완성된 조각은 자리표시자로 치워 둔다

인라인 코드는 원래부터 이 문제를 비슷한 방식으로 피하고 있었습니다. 코드 안의 글자는 다른 문법을 적용하면 안 되니, 코드를 HTML로 바꾸자마자 그 자리를 `\u0000숫자\u0000` 같은 눈에 띄지 않는 자리표시자로 바꿔 두고, 모든 처리가 끝난 뒤 마지막에 원래 HTML로 되돌려 놓는 방식입니다.

이번에 고친 내용은 이 방식을 이미지와 링크에도 그대로 적용한 것입니다.

```js
const parts = [];
const hold = (html) => {
  parts.push(html);
  return `\u0000${parts.length - 1}\u0000`;
};

// 링크를 만들자마자 자리표시자로 치운다
s = s.replace(/\[([^\]]+)\]\(((?:[^()\s]|\([^()\s]*\))+)\)/g, (_, label, href) => {
  const h = safeUrl(href);
  return hold(`<a href="${h}">${renderEmphasis(label)}</a>`);
});

// 이제 기울임 정규식이 문자열을 훑어도 href 는 이미 자리표시자(숫자)일 뿐이다
s = renderEmphasis(s);

// 마지막에 자리표시자를 실제 HTML 로 되돌린다
s = s.replace(/\u0000(\d+)\u0000/g, (_, i) => parts[Number(i)]);
```

링크 라벨 자체에는 강조를 먹여야 하니(`[**중요**한 글](url)` 같은 경우), 라벨만 따로 `renderEmphasis`를 먼저 돌리고 완성된 `<a>` 태그를 통째로 치워 둡니다. 뒤따르는 정규식 눈에는 href 속성값이 더는 보이지 않고, 숫자 하나만 보입니다.

## 왜 여태 안 드러났나

이 블로그에 지금까지 쓴 글 중에는 주소에 `*`가 들어간 링크가 하나도 없었습니다. 그래서 버그가 있어도 겉으로는 멀쩡해 보였습니다. 고치기 전에 일부러 `*release*`가 든 링크로 재현해서 실제로 깨지는 걸 먼저 확인하고, 그다음에 고쳤습니다. 코드를 고치고 나서 "이제 맞겠지"라고 넘어가는 것과, 고치기 전에 문제를 직접 눈으로 본 다음 고치는 것은 디버깅에서 다른 수준의 확신을 줍니다.

## 오늘의 한 줄 정리

> 여러 정규식을 순서대로 돌릴 때, 완성된 결과는 다음 정규식의 눈에 안 보이게 치워 둬야 한다 — 정규식은 자기 앞에 있는 게 아직 처리 중인 원문인지 이미 끝난 결과물인지 구별하지 못한다.

## 확인이 필요한 부분

- 이번 글은 코드 리뷰에서 나온 10건 중 마크다운 파서 관련 1건만 다뤘습니다. `js/app.js`의 라우팅 경쟁 조건, `js/theme.js`의 테마 값 검증 등 같은 리뷰에서 함께 고친 나머지 항목은 다루지 않았습니다 — 다음 편 소재로 남겨둘지 결정이 필요합니다.
- 자리표시자 복원을 "최대 5번 반복"하도록 상한을 둔 이유(중첩된 자리표시자가 생길 수 있는 경우)는 커밋 메시지에 간단히만 적혀 있어, 실제로 몇 겹까지 중첩될 수 있는지는 코드를 더 봐야 압니다.
- 이 기간 동안 스도쿠·포모도로 두 미니 웹앱과 카테고리 구조 개편도 있었는데, 분량상 이번 편에서는 다루지 않았습니다. 사람이 보기에 더 먼저 다뤘어야 할 소재라면 순서를 조정해 주세요.
