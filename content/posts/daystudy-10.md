지난 글(Daystudy #3) 이후 이 저장소는 꽤 멀리 왔습니다. 미니 웹앱 두 개(스도쿠, 포모도로)가 `/apps/` 아래 생겼고, 그 목록을 `content/apps.json`이 `posts.json`과 같은 방식으로 책임지게 됐습니다. 그리고 최근 커밋에서 블로그 본체(`index.html`, `js/`)가 처음으로 코드 리뷰를 받았습니다 — 그동안의 review.md 두 개는 웹앱만 다뤘으니까요. 리뷰가 찾은 10건 중 세 가지가 "왜 이런 버그가 생기는가"를 특히 잘 보여줘서, 오늘은 그것만 정리합니다.

## 완성된 HTML을 정규식이 다시 훑는다

`js/markdown.js`는 `[라벨](주소)` 같은 링크 문법을 `<a href="주소">라벨</a>`로 바꾸고, 그다음에 `*기울임*` 같은 강조 문법을 처리합니다. 문제는 두 처리가 **같은 문자열 위에서** 순서대로 일어난다는 점입니다. 링크를 먼저 완성해 놓으면, 뒤이어 도는 강조용 정규식이 자기가 만든 `href="..."` 속성값 안쪽까지 "텍스트"로 보고 훑어 버립니다.

```
[배포 노트](https://example.com/*release*)
```

의도한 결과는 `href="https://example.com/*release*"` 인데, 강조 정규식이 `*release*`를 찾아 이렇게 바꿔 버립니다.

```
href="https://example.com/<em>release</em>"
```

주소 안에 HTML 태그가 끼어들어 링크가 깨집니다. 에러가 나는 게 아니라 **조용히 엉뚱한 주소로 가는** 버그라서 테스트에서도 눈에 잘 안 띕니다. 지금까지 쓴 글에는 `*`가 든 URL이 없어서 이 버그가 드러나지 않았을 뿐이었습니다.

고친 방법은 "완성된 조각은 다음 단계가 못 건드리게 치워 둔다"입니다. 코드 → 이미지 → 링크를 만들 때마다 결과를 바로 쓰지 않고, 목록에 넣어 둔 뒤 `\u0000번호\u0000` 같은 자리표시자로 바꿔 놓습니다. 강조 처리는 이 자리표시자만 보니 안쪽 HTML을 건드릴 일이 없고, 맨 마지막에 자리표시자를 원래 조각으로 되돌립니다. 포장을 마친 상자는 테이프로 봉하고, 그다음 작업은 상자 겉면만 보게 하는 셈입니다.

## 늦게 끝난 요청이 화면을 덮는다

주소(해시)가 빠르게 바뀌면, 먼저 시작한 데이터 적재가 나중에 끝날 수 있습니다. 예를 들어 글 A를 열자마자 글 B로 넘어갔는데, A를 불러오던 `fetch`가 B보다 늦게 끝나면 — B 화면이 떠 있는데 A의 내용이 뒤늦게 덮어씁니다. 주소는 B인데 화면은 A인 상태가 됩니다.

고친 방법은 "세대 번호"입니다. 화면을 바꿀 때마다 번호를 하나 올리고, 그 번호를 들고 비동기 작업을 시작합니다. 작업이 끝났을 때 번호가 최신인지 확인하고, 아니면 화면을 건드리지 않고 그냥 버립니다.

```js
let routeVersion = 0;
const stale = version => version !== routeVersion;

function show(node, title, version) {
  if (stale(version)) return;
  // ...화면 교체
}
```

번호를 들고 다니지 않으면 "지금 이 결과가 아직 유효한가"를 판단할 방법이 없습니다. 비동기 작업은 시작한 순서대로 끝난다는 보장이 없다는 걸 코드로 직접 확인한 셈입니다.

## "파싱된다"와 "내용이 멀쩡하다"는 다른 이야기

`posts.json`은 JSON 문법만 맞으면 `JSON.parse`가 통과시킵니다. 하지만 `slug`나 `title`이 빈 문자열이거나 통째로 빠진 항목도 문법적으로는 멀쩡한 JSON입니다. 그런 항목이 섞여 들어오면 `posts.sort(...)` 같은 코드가 알아들을 수 없는 메시지로 죽습니다.

이게 가정이 아닌 이유는, 이 블로그의 Daystudy 글이 매일 저녁 클라우드 루틴이 PR로 `posts.json`을 고치는 방식으로 늘어나기 때문입니다 — 지금 이 글도 그렇게 올라갑니다. 사람이 아닌 자동화가 매일 데이터 파일을 건드리는 경로가 실제로 있으니, "필드가 비었거나 배열이 아닌 경우"를 미리 막아 둬야 합니다.

```js
function checkPosts(value) {
  for (const p of checkArray(value, '글 목록')) {
    if (!p || !filled(p.slug) || !filled(p.title) || !filled(p.date) || !filled(p.category)) {
      throw new Error('글 목록에 필수 정보(slug · title · date · category)가 빠진 항목이 있어요.');
    }
  }
  return value;
}
```

JSON이 깨졌을 때도, 필드가 빠졌을 때도 사용자는 콘솔 에러 대신 읽을 수 있는 한국어 문장을 보게 됩니다. "파싱 가능"과 "쓸 수 있는 데이터"는 서로 다른 기준이라는 걸, 데이터를 매일 고치는 자동화를 만들고 나서야 코드에 반영하게 됐습니다.

## 확인이 필요한 부분

- 리뷰가 찾은 나머지 7건(중간 4·낮음 5 중 이 글에 안 담은 것들)은 `codex-review.md`에 있습니다. 내용을 더 보고 싶으면 그 파일을 확인해 주세요.
- 마크다운 파서의 XSS 방어(이스케이프 순서, `safeUrl`이 `javascript:`·`data:`·`vbscript:`를 막는 방식)를 어떤 입력으로 직접 시험했는지는 커밋 메시지만으로는 재구성하지 못했습니다.
- 스도쿠·포모도로 두 웹앱과 `apps.json` 데이터 패턴 자체는 이번 글에 담지 않았습니다. 다음 Daystudy 글감으로 남겨 둡니다.

## 오늘의 한 줄 정리

- 완성된 문자열(예: 만들어진 `href`)을 다음 정규식이 다시 훑으면 안의 내용까지 패턴으로 오인한다. 끝난 조각은 자리표시자로 치워 둔다.
- 비동기 작업은 시작한 순서대로 끝난다는 보장이 없다. "지금 이 결과가 유효한가"를 판단할 번호가 따로 필요하다.
- JSON이 파싱된다는 것과 데이터가 멀쩡하다는 것은 다른 이야기다. 자동화가 매일 데이터 파일을 고치는 경로가 있다면 필드 검증은 선택이 아니다.
