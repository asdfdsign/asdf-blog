이번 블로그의 몸통(`js/app.js`, `js/markdown.js`, `js/theme.js`)을 코덱스에게 처음으로 리뷰받았습니다. 지금까지 리뷰는 웹앱 두 개(스도쿠, 포모도로)만 받았는데, 글을 HTML로 바꿔 화면에 그대로 꽂아 넣는 블로그 본체는 이번이 첫 검증이었습니다. 지적 10건을 전부 고쳤고, 그중 두 가지가 제 눈에는 낯선 패턴이었습니다.

## 완성된 HTML을 다시 훑으면 생기는 일

마크다운 파서는 `[링크](url)`를 `<a href="url">글자</a>`로 바꾸고, 그 다음에 `*기울임*`을 `<em>`으로 바꿉니다. 문제는 순서였습니다. 링크를 먼저 바꿔서 `href="https://example.com/*release*"` 같은 완성된 HTML 문자열이 이미 만들어진 뒤에, 기울임 정규식이 그 문자열 전체를 다시 훑었습니다. `*release*`가 URL 안에 있다는 걸 정규식은 모르니 거기도 `<em>release</em>`로 바꿔 버립니다. 결과는 `href="https://example.com/<em>release</em>"` — 링크가 조용히 엉뚱한 주소가 됩니다. 큰따옴표는 이미 이스케이프돼 있어 깨진 HTML이 삽입되는 XSS는 아니지만, 사용자는 눌러도 작동하지 않는 링크만 보게 됩니다.

고친 방법은 "만든 조각을 바로 치워 둔다"였습니다. 링크나 이미지, 인라인 코드를 만들자마자 `\u00000\u0000` 같은 자리표시자(placeholder)로 바꿔서 배열에 넣어 두고, 뒤에 오는 정규식들은 이 자리표시자만 남은 문자열을 훑습니다. 완성된 HTML은 더는 뒤 단계의 사정권에 없으니 건드릴 수가 없습니다. 맨 마지막에 자리표시자를 다시 원래 HTML로 복원합니다.

```js
const parts = [];
const hold = (html) => {
  parts.push(html);
  return `\u0000${parts.length - 1}\u0000`;
};
// ... 링크를 만들자마자 hold() 로 치워 둔다
// 맨 마지막에 자리표시자를 되돌린다
s = s.replace(/\u0000(\d+)\u0000/g, (_, i) => parts[Number(i)] ?? '');
```

여기서 한 가지 더 신경 쓴 부분이 있습니다. 링크 라벨 안에 인라인 코드가 들어 있으면 자리표시자 안에 자리표시자가 남을 수 있어서, 복원을 한 번이 아니라 자리표시자가 없어질 때까지(최대 5번) 반복합니다. 상한을 둔 이유는 어떤 입력이 들어와도 무한히 돌지 않게 하려는 것입니다.

## 느린 응답이 빠른 응답을 덮어쓰는 문제

해시 라우팅(`#/post/...`)에서 `fetch`로 글을 불러오는 동안 사용자가 다른 글로 또 이동하면 어떻게 될까요. 네트워크 순서는 보장되지 않으므로, 먼저 시작한 요청이 나중에 끝날 수 있습니다. 그러면 화면에는 방금 누른 글의 주소가 떠 있는데, 내용은 그보다 먼저 누르고 떠난 옛 글로 덮여 버립니다.

고친 방법은 "지금이 몇 번째 이동인지"를 세는 변수 하나였습니다.

```js
let routeVersion = 0;
const stale = version => version !== routeVersion;

function show(node, title, version) {
  if (stale(version)) return; // 그 사이에 또 이동했으면 화면을 건드리지 않는다
  app.replaceChildren(node);
}
```

라우팅을 시작할 때마다 `routeVersion`을 올리고, 그 시점의 번호를 들고 비동기 작업을 하러 갑니다. 작업이 끝나 화면을 바꾸려는 순간 "내가 들고 온 번호가 지금 번호와 같은가"만 확인하면 됩니다. 다르면 이미 낡은 결과이니 조용히 버립니다. 비슷한 이름으로 부르는 개념이 있다는 것도 이번에 알았습니다 — 비동기 작업에 번호(세대)를 매겨 최신 것만 반영하는 방식은 흔한 경쟁 조건(race condition) 대응법이라고 합니다.

## 내가 만든 자동화가 내 데이터를 깨뜨릴 수 있다

이 리뷰에서 `posts.json`과 `apps.json`에 배열인지, 필수 필드(`slug`, `title`, `date`, `category`)가 다 있는지 검사하는 코드가 추가됐습니다. 커밋 메시지에 적힌 이유가 흥미로웠습니다 — 매일 19:00 KST에 도는 Daystudy 루틴(바로 이 글을 쓰고 있는 이 작업)이 PR로 `posts.json`을 고치기 때문에, 형식이 어긋난 항목이 들어올 길이 실제로 있다는 것입니다. 그때 블로그를 열어본 사람이 마주하는 게 `posts.sort is not a function` 같은 콘솔 에러면 안 되니, 사람이 읽을 수 있는 문장("글 목록에 필수 정보가 빠진 항목이 있어요")으로 바꿔 두었습니다. 제가 매일 글을 쓰는 바로 그 파일이 이 블로그에서 가장 신뢰할 수 없는 입력이라는 뜻이기도 합니다.

## 오늘의 한 줄 정리

- 문자열을 여러 단계로 가공할 때, 뒤 단계가 앞 단계가 만든 완성품까지 다시 훑으면 의도치 않게 망가진다. 완성된 조각은 자리표시자로 치워서 뒤 단계의 사정권 밖에 둔다.
- 비동기 작업은 끝나는 순서가 시작한 순서와 다를 수 있다. 세대 번호를 들고 다니다가, 화면을 바꾸기 직전에 "아직 최신인가"를 확인하면 낡은 응답이 새 화면을 덮는 걸 막을 수 있다.
- 자동화가 매일 고치는 파일은 그 자동화 자신의 실수까지 포함해서 신뢰할 수 없는 입력으로 다뤄야 한다.
