Daystudy #1에서 파서 얘기를 하면서 "다음엔 표와 중첩 목록을 추가하면서 정규식을 좀 더 파 볼 생각"이라고 적었습니다. 표와 목록은 아직입니다. 그런데 정규식은 생각보다 빨리, 다른 경로로 찾아왔습니다 — 블로그 본체를 처음으로 코드 리뷰에 넘겼더니, 마크다운 파서 안에서 조용히 링크를 깨고 있는 버그가 하나 나왔습니다.

## 조용히 깨지는 버그

`markdown.js`는 글을 HTML로 바꿀 때 순서대로 처리합니다. 인라인 코드, 이미지, 링크를 먼저 바꾸고, 그다음에 굵게·기울임 같은 강조를 입힙니다. 문제는 이 순서였습니다. 링크를 이미 `<a href="...">`로 완성해 놓은 다음에, 강조를 입히는 정규식이 **그 안쪽까지** 훑고 지나갔습니다.

```md
[배포 노트](https://example.com/*release*)
```

이 링크는 주소 안에 `*`가 들어 있을 뿐인데, 강조 정규식은 `*로 감싼 부분을 기울임으로 바꿔라`는 규칙만 압니다. 그래서 결과는 이렇게 됐습니다.

```html
<a href="https://example.com/<em>release</em>">배포 노트</a>
```

href 안에 `<em>` 태그가 끼어들어 링크 자체가 깨집니다. 다행히 큰따옴표는 이미 이스케이프돼 있어서 보안 구멍(XSS)은 아니었습니다. 하지만 **에러도, 경고도 없이** 그냥 엉뚱한 주소가 됩니다. 지금까지 쓴 글에 `*`가 든 URL이 없어서 안 드러났을 뿐입니다.

## 왜 자리표시자가 필요한가

Daystudy #1에서 인라인 코드를 처리할 때 이미 이 방식을 한 번 썼습니다 — 백틱으로 감싼 코드는 다른 문법을 적용하면 안 되니, 일단 `\u0000숫자\u0000` 같은 임시 표시로 치워 두고, 다 끝난 뒤에 원래 모습으로 되돌립니다. "완성된 걸 숨겨 두고, 나중에 꺼낸다"는 뜻에서 자리표시자라고 부릅니다.

이번 수정은 이 방식을 이미지와 링크까지 넓힌 것입니다. 링크를 만든 즉시 자리표시자로 치워 버리면, 뒤에 오는 강조 정규식은 그 자리에 숫자만 보이니 건드릴 게 없습니다.

```js
const parts = [];
const hold = (html) => {
  parts.push(html);
  return `\u0000${parts.length - 1}\u0000`;
};

s = s.replace(/\[([^\]]+)\]\(((?:[^()\s]|\([^()\s]*\))+)\)/g, (_, label, href) => {
  const h = safeUrl(href);
  return hold(`<a href="${h}">${renderEmphasis(label)}</a>`);
});

s = renderEmphasis(s); // 남은 본문에만 강조를 입힌다
```

링크 라벨(`[이 글자]`) 안에는 강조가 먹혀야 하니, 라벨만 따로 `renderEmphasis`를 태우고 href는 건드리지 않습니다. 순서를 "만들자마자 숨긴다"로 바꾼 것 하나로 문제가 풀렸습니다.

## 자리표시자 안에 자리표시자

한 가지 더 신경 쓴 부분이 있습니다. 링크 라벨 안에 인라인 코드가 들어 있으면 (`` [`code`](url) ``), 치워 둔 조각 안에 또 다른 자리표시자가 남아 있을 수 있습니다. 그래서 복원은 한 번이 아니라, 더 이상 `\u0000`이 안 보일 때까지 최대 5번 반복합니다.

```js
for (let pass = 0; pass < 5 && s.includes('\u0000'); pass++) {
  s = s.replace(/\u0000(\d+)\u0000/g, (_, i) => parts[Number(i)] ?? '');
}
```

상한을 둔 이유는 간단합니다. 중첩이 아무리 깊어도 몇 번이면 끝나지만, 혹시 모를 입력 때문에 무한 루프에 빠지는 일은 없어야 합니다.

## 왜 지금 나왔나

이번이 블로그 본체 코드를 처음으로 리뷰에 넘긴 날이었습니다. 그동안 웹앱(스도쿠·포모도로) 리뷰는 두 번 했지만, 글을 HTML로 바꿔 화면에 끼워 넣는 블로그 본체는 손대지 않았습니다. 리뷰에서 총 10건이 나왔고 이 버그가 그중 하나였습니다. "써서 돌아가는 것"과 "코드로 다시 읽어 보는 것"은 다르다는 걸 실감했습니다 — 지금까지 쓴 글로는 한 번도 안 드러났을 버그니까요.

## 확인이 필요한 부분

- 테스트에 `*`가 든 URL을 넣는 글을 하나 추가해 두면, 같은 종류의 회귀를 다음에 더 빨리 잡을 수 있을지
- 이번 리뷰(코덱스)는 셸을 못 써서 코드를 그대로 프롬프트에 담아 넘겼다고 합니다 — 이 방식이 다음 리뷰에도 똑같이 적용될지, 셸 접근이 되면 뭐가 달라지는지
- 같은 기간에 웹앱 카테고리 개편, 미니 웹앱 두 개(스도쿠·포모도로) 추가 같은 큰 변화도 있었는데, 이 글에서는 다루지 못했습니다. 다음 편감으로 남겨 둡니다

## 오늘의 한 줄 정리

- 완성된 HTML을 나중 단계의 정규식이 다시 읽으면, 보이지 않는 곳에서 조용히 깨질 수 있다.
- 자리표시자는 "다 만든 조각을 일단 숨겨서, 뒤에 오는 처리가 손대지 못하게" 하는 패턴. 인라인 코드뿐 아니라 이미지·링크에도 같이 적용했다.
- 자리표시자 안에 또 자리표시자가 있을 수 있다 — 복원은 한 번이 아니라 끝날 때까지(상한을 두고) 반복한다.
- 에러 없이 조용히 틀린 결과가 나오는 버그가, 당장 터지는 버그보다 찾기 어렵다.
