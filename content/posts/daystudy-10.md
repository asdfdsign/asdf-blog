블로그 본체 코드를 코덱스에게 처음으로 리뷰받았습니다. 그동안 리뷰는 두 웹앱(스도쿠·포모도로)만 받았고, 글을 HTML로 바꿔 화면에 끼워 넣는 블로그 본체는 이번이 첫 리뷰입니다. 10건이 나왔고 전부 고쳤는데, 그중 마크다운 파서에서 나온 버그 하나가 "정규식을 쓸 때 순서가 왜 중요한가"를 가장 또렷하게 보여줬습니다.

## 어떤 버그였나

이 블로그의 `markdown.js`는 `[글자](주소)` 모양을 보면 `<a href="주소">글자</a>`로 바꿉니다. 그리고 `*글자*` 모양을 보면 `<em>글자</em>`로 바꿉니다. 둘 다 정규식(패턴을 찾아 바꾸는 도구)으로 되어 있고, 순서대로 한 번씩 돕니다. 문제는 **링크를 먼저 만들고, 그 결과물 위에서 강조 정규식을 또 돌렸다**는 것입니다.

이런 글이 있다고 하면:

```md
[배포 노트](https://example.com/*release*)
```

링크를 먼저 바꾸면 이렇게 됩니다.

```html
<a href="https://example.com/*release*">배포 노트</a>
```

그다음 강조 정규식이 전체 텍스트를 다시 훑습니다. 이 정규식은 "링크 태그 안인지"를 모릅니다. 그냥 글자만 보고 `*...*`를 찾아 `<em>...</em>`으로 바꿉니다. 그래서 `href` 속성 안의 `*release*`까지 걸려듭니다.

```html
<a href="https://example.com/<em>release</em>">배포 노트</a>
```

주소가 깨졌습니다. 큰따옴표는 이미 이스케이프되어 있어서 XSS(악성 스크립트 삽입)로는 번지지 않았지만, 링크는 조용히 엉뚱한 곳으로 가게 됩니다. 지금까지 쓴 글에는 주소에 `*`가 든 경우가 없어서 드러나지 않았을 뿐입니다.

## 왜 이런 일이 생기나

원인은 **완성된 결과물을 다시 재료로 취급했다**는 점입니다. `<a href="...">` 는 "다 만들어진 HTML 태그"인데, 강조 정규식에게는 그냥 글자일 뿐입니다. 요리에 비유하면, 접시에 올린 완성 요리에 "소금 뿌리기"를 또 돌리는 것과 같습니다. 재료 단계에서 뿌렸어야 할 소금이 이미 완성된 요리의 포장지(속성값) 위에 떨어집니다.

## 고친 방법 — 자리표시자

해법은 코드·이미지·링크를 만든 **즉시 숨겨 두는 것**입니다. 완성된 HTML 조각을 배열에 저장해 두고, 그 자리에는 `\u00003\u0000` 같은 짧은 표시만 남깁니다. 뒤에 오는 정규식들은 이 표시를 글자로 보기 때문에 안을 들여다볼 일이 없습니다. 모든 정규식이 끝난 뒤, 마지막에 표시를 찾아 저장해 둔 진짜 HTML로 되돌립니다.

```js
const parts = [];
const hold = (html) => {
  parts.push(html);
  return `\u0000${parts.length - 1}\u0000`;
};

// 링크를 만들자마자 치워 둔다
s = s.replace(/\[([^\]]+)\]\(([^)]+)\)/g, (_, label, href) => {
  return hold(`<a href="${safeUrl(href)}">${renderEmphasis(label)}</a>`);
});

// 이후 정규식들은 \u0000 표시만 보고 지나간다
s = renderEmphasis(s);

// 맨 마지막에 되돌린다
s = s.replace(/\u0000(\d+)\u0000/g, (_, i) => parts[Number(i)]);
```

순서를 정리하면 이렇습니다.

> 코드 → 이미지 → 링크(라벨만 강조 적용 후 통째로 숨김) → 남은 본문 강조 → 표시 복원

링크의 **라벨**(글자 부분)은 강조를 적용해야 하니 숨기기 전에 따로 처리하고, href 같은 속성값은 숨긴 채로 유지됩니다. 숨긴 조각 안에 또 다른 숨긴 조각이 들어 있을 수 있어서(링크 라벨 안에 인라인 코드가 있는 경우 등) 복원은 표시가 더 안 남을 때까지 몇 번 반복합니다.

## 같은 리뷰에서 나온 다른 교훈

이 리뷰에서 눈에 걸린 지적이 하나 더 있었습니다. `posts.json`은 사람이 직접 고치는 파일이 아니라, **매일 밤 Daystudy 루틴이 PR로 고치는 파일**이기도 합니다. 지금 이 글을 쓰고 있는 것도 그 루틴입니다. 그래서 `app.js`에 배열인지, 필수 항목이 다 있는지를 확인하는 코드가 추가됐습니다. 루틴이 실수로 깨진 JSON을 올리면 사람이 볼 화면이 `posts.sort is not a function` 같은 에러가 아니라 읽을 수 있는 문장이어야 한다는 이유였습니다.

두 버그는 닮은 구조입니다. 사용자가 입력한 글만 조심하면 된다고 생각했는데, **내 자동화가 만든 데이터도 똑같이 의심해야 할 입력**이었습니다.

## 오늘의 한 줄 정리

- 정규식으로 이미 완성한 HTML을 다른 정규식으로 다시 훑으면, 속성값 안의 글자까지 건드릴 수 있다.
- 완성된 조각은 자리표시자로 숨겨 두고, 모든 처리가 끝난 뒤 마지막에 복원한다.
- 지금 글에서 안 터졌다고 안전한 게 아니다 — 조건(주소에 `*`가 들어가는 경우)이 아직 안 왔을 뿐이다.
- 믿으면 안 되는 입력은 사용자뿐 아니라, 매일 자동으로 파일을 고치는 내 자신의 루틴도 포함된다.

## 확인이 필요한 부분

- `renderEmphasis`에서 굵게(`**`)와 기울임(`*`)을 가르는 정규식이 중첩된 경우(`**굵게 안에 *기울임***` 같은 모양)까지 확인했는지는 커밋 메시지만으로는 알 수 없습니다. 실제 글로 시험해 볼 필요가 있습니다.
- 자리표시자 복원 루프의 반복 상한(5회)이 왜 5인지, 더 깊은 중첩이 실제로 나올 수 있는지는 코드만으로는 판단이 안 됩니다.
- `posts.json` 검증 로직이 어떤 구체적인 오류 문장을 보여주는지는 이 글에서 직접 확인하지 못했습니다. 브라우저에서 깨진 JSON을 넣어 실제 화면을 봐야 합니다.
