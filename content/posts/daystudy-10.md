지금까지 코드 리뷰는 웹앱(스도쿠·포모도로) 쪽만 받았습니다. 블로그 본체 — 글을 마크다운에서 HTML로 바꿔 화면에 꽂아 넣는 `js/app.js`, `js/markdown.js` — 는 이번이 첫 리뷰였습니다. 코덱스가 10건을 찾았고(높음 1·중간 4·낮음 5), 치명적인 건 없었습니다. 그중 두 개가 "왜 지금까지 안 터졌는지"가 흥미로워서 정리해 둡니다.

## 레이스 컨디션: 해시가 빨리 바뀔 때

카테고리 A를 누르면 `loadIndex()`가 `fetch`를 보냅니다. 응답이 오기 전에 사용자가 카테고리 B를 눌러 버리면 어떻게 될까요. 네트워크 속도가 들쭉날쭉하면 **B의 요청이 먼저 끝나 화면을 그리고, 그 다음에야 늦게 도착한 A의 응답이 그 화면을 덮어씁니다.** 주소창은 B인데 화면은 A인 상태가 됩니다.

고친 방법은 "지금 이 요청이 아직 최신인가"를 버전 번호로 들고 다니는 것이었습니다.

```js
let routeVersion = 0;
const stale = version => version !== routeVersion;

function show(node, title, version) {
  if (stale(version)) return;
  app.replaceChildren(node);
  // ...
}
```

라우팅이 시작될 때마다 `routeVersion`을 올리고, 그 순간의 번호를 모든 비동기 함수에 끝까지 들려 보냅니다. `fetch`가 끝나고 돌아왔을 때, 화면을 실제로 바꾸기 직전마다 `stale(version)`으로 "내가 아직 최신 요청인가"를 다시 확인합니다. 늦게 끝난 A는 자기 번호가 이미 낡았다는 걸 알고 조용히 멈춥니다. 비동기 작업은 시작한 순서대로 끝난다는 보장이 없다는 걸, 화면이 실제로 어긋나는 걸 봐야 체감하게 되는 것 같습니다.

## 탐욕적 정규식이 멀쩡한 링크를 깨뜨린 사례

마크다운 파서는 코드 → 이미지 → 링크 → 강조 순서로 문법을 처리합니다. 링크를 먼저 `<a href="...">`로 만들고, 그 다음에 굵게·기울임 정규식을 전체 문자열에 돌리는 구조였습니다. 문제는 이 정규식이 "지금부터 만든 HTML"과 "아직 처리 안 한 원문"을 구분하지 못한다는 것이었습니다.

```
[배포 노트](https://example.com/*release*)
→ href="https://example.com/<em>release</em>"
```

링크는 이미 완성됐는데, 기울임 정규식(`*...*`)이 그 `href` 속성값 안쪽의 `*release*`까지 찾아내 태그로 바꿔 버립니다. 주소가 깨지는데 에러도 안 뜹니다. 지금까지 쓴 글에는 URL에 `*`가 들어간 경우가 없어서 드러나지 않았을 뿐입니다.

고친 방법은 인라인 코드에 쓰던 수법을 링크·이미지에도 그대로 적용하는 것이었습니다. HTML을 만드는 즉시 `\u00000\u0000` 같은 자리표시자로 바꿔 치워 두고, 강조 처리가 다 끝난 뒤에 되돌립니다.

```js
const parts = [];
const hold = (html) => {
  parts.push(html);
  return `\u0000${parts.length - 1}\u0000`;
};
```

이렇게 하면 강조 정규식이 훑는 문자열에는 이미 만들어진 HTML이 아니라 숫자 자리표시자만 남습니다. 완성된 속성값을 다시 건드릴 길이 없어집니다.

## 방어적 JSON 검증이 필요해진 이유

`content/posts.json`은 매일 19:00 Daystudy 루틴이 PR로 고치는 파일입니다 — 바로 이 글도 그렇게 올라갑니다. 즉 "형식이 깨진 항목이 들어올 경로"가 실제로 존재합니다. 그런 날 사용자가 보게 되는 게 `posts.sort is not a function` 같은 내부 에러 문장이면 안 됩니다.

```js
function checkArray(value, what) {
  if (!Array.isArray(value)) throw new Error(`${what} 형식이 올바르지 않아요. 목록(배열)이어야 해요.`);
  return value;
}
```

배열인지, `slug`·`title`·`date`·`category` 같은 필수 필드가 채워져 있는지를 받는 즉시 검사하고, 어긋나면 사람이 읽을 수 있는 한국어 문장으로 바꿔 던집니다. JSON이 **파싱된다는 것**과 **내용이 멀쩡하다는 것**은 다른 이야기라는 걸, 그 파일을 매일 자동으로 고치는 구조를 만들고 나서야 신경 쓰게 됐습니다.

## 확인이 필요한 부분

- 커밋 메시지에는 "회귀 없음(홈 12·Daystudy 9·웹앱 2, 375px 가로 스크롤 0, 콘솔 오류 없음)"이라고만 적혀 있어, 그 검증을 정확히 어떤 절차로 했는지는 이 글만으로는 알 수 없습니다.
- 레이스 컨디션 재현에 쓴 "느린 적재 중 해시 전환" 시나리오를 실제로 어떻게 만들었는지(네트워크 쓰로틀링 등)는 커밋 로그에 나오지 않습니다.
- 코덱스가 셸을 쓸 수 없어 코드를 프롬프트로만 받아 리뷰했다고 되어 있는데, 그 제약이 이번 리뷰의 발견 범위에 어떤 영향을 줬는지는 다루지 않았습니다.

## 오늘의 한 줄 정리

- 비동기 작업은 시작한 순서대로 끝나지 않는다. 화면을 바꾸기 직전마다 "나 아직 최신 요청 맞아?"를 버전 번호로 확인해야 한다.
- 정규식으로 이미 만든 HTML 위를 다시 훑으면 완성된 속성값까지 건드려 조용히 깨질 수 있다. 자리표시자로 치워 두는 게 안전하다.
- 매일 자동으로 고쳐지는 파일은 입력으로 다뤄야 한다. 파싱되는 것과 내용이 맞는 것은 다른 문제다.
