지난 편 이후 커밋을 보니 대부분이 `.claude/permissions.md` 와 `.claude/settings.json` 을 고치는 과정이었습니다. 클로드 코드가 어떤 모드에서도 실행하지 못하게 막는 "차단 규칙(deny)"을 새로 만들고, 오탐을 하나씩 잡아 나간 기록입니다. 규칙을 고치면서 글자 패턴으로 뭔가를 막는다는 것의 한계가 보였습니다.

## 두 겹의 안전장치는 다른 일을 한다

처음에는 옵시디언 볼트(개인 노트 폴더)의 하위 폴더마다 `Edit/Write` 차단 규칙을 하나씩 적어 18줄을 만들었습니다. 그런데 이 프로젝트에는 이미 **샌드박스**라는 게 있었습니다. 샌드박스는 프로젝트 폴더 밖에 파일을 쓰는 것 자체를 막는 장치입니다.

```json
"sandbox": {
  "filesystem": { "allowWrite": ["D:/Documents/Obsidian Vault/블로그"] }
}
```

`allowWrite` 는 딱 이 한 폴더만 열어 두고 나머지는 전부 잠급니다. 그러니 볼트 폴더마다 deny 규칙을 따로 적는 건 **이미 잠긴 문을 한 번 더 잠그는 것**이었습니다. 18줄을 지우고 나니 나머지 규칙이 훨씬 잘 보였습니다.

```
샌드박스: "이 폴더 밖은 건드릴 수 없다" (허용 목록, allow)
deny 규칙: "이 명령은 어디서든 못 한다" (차단 목록, block)
```

같은 결과(막힘)를 내는 장치라도 **허용 목록으로 막는 것**과 **금지 목록으로 막는 것**은 다른 장치라는 걸 알게 됐습니다. 하나가 있다고 다른 하나가 필요 없어지는 건 아니지만, 둘이 정확히 같은 일을 중복해서 하고 있다면 하나는 덜어내도 됩니다.

## 규칙은 글자 모양만 본다

deny 규칙은 `Bash(rd /s*)` 처럼 **문자열이 이렇게 시작하면 막는다**는 식으로 적힙니다. 이번에 고친 두 가지가 그 한계를 잘 보여줬습니다.

**너무 좁아서 못 잡는 경우.** Windows 의 폴더 삭제 명령 `Remove-Item -Recurse` 를 막는 규칙을 처음엔 `Bash(Remove-Item *-Recurse*)` 로만 적었습니다. 그런데 `powershell -Command "Remove-Item ... -Recurse"` 처럼 **셸로 한 번 감싸서** 부르면 문자열이 `powershell` 로 시작해 규칙에 안 걸립니다. 앞에 와일드카드를 붙여야 했습니다.

```
Bash(Remove-Item *-Recurse*)   →  Bash(*Remove-Item *-Recurse*)
```

**너무 넓어서 엉뚱한 걸 잡는 경우.** 반대로 `rd /s` (폴더 삭제) 를 막으려 만든 규칙에 앞뒤로 와일드카드를 붙였더니, `record /sec` 같은 전혀 무관한 명령 글자에도 걸렸습니다. `rd /s` 자체가 다섯 글자뿐이라 아무 데나 끼어 있을 수 있었습니다. 그래서 이런 짧은 명령은 앞 와일드카드를 빼고 **줄 맨 앞에서 시작할 때만** 잡도록 좁혔습니다.

두 실수는 반대 방향이지만 원인은 같습니다. **규칙은 명령의 의도를 모르고 글자 모양만 봅니다.** 너무 좁게 적으면 우회한 호출을 놓치고, 너무 넓게 적으면 죄 없는 명령까지 막습니다. 둘 다 실제로 명령을 시험해 보기 전에는 알기 어려웠습니다.

## 위험도 모양으로는 다 가려지지 않는다

`git push --force` 는 deny 목록에 있지만 `git push --force-with-lease` 는 뺐습니다. 둘 다 "강제로 덮어쓴다"는 점에서 이름은 비슷해 보입니다. 차이는 동작에 있습니다.

- `--force`: 내가 아는 원격 상태와 상관없이 무조건 덮어씁니다.
- `--force-with-lease`: 내가 마지막으로 본 원격 상태와 지금 원격이 같을 때만 덮어씁니다. 그사이 누가 먼저 푸시했다면 거부됩니다.

이름만 보고 "force가 들어가니까 위험하다"로 묶으면 틀립니다. 규칙을 글자 패턴으로 적다 보니 자꾸 "비슷해 보이는 걸 한 덩어리로 막고 싶은" 유혹이 생기는데, 실제 위험은 명령어 텍스트가 아니라 **동작의 조건**에 있었습니다.

## 확인이 필요한 부분

- `Bash(*Remove-Item *-Recurse*)` 와 `Bash(rd /s*)` 를 실제 Windows 환경에서 직접 시험해 차단되는지 확인이 필요합니다 (이 세션은 리눅스 컨테이너라 실행해 보지 못했습니다).
- 공통 규칙 개수가 커밋마다 22 → 24 → 26 → 27개로 바뀌었는데, 지금 실제 개수와 `.claude/permissions.md` 표의 숫자가 맞는지 한 번 더 세어 확인이 필요합니다.
- `record /sec` 오탐 사례가 실제로 어떤 상황에서 나왔는지(어떤 명령을 실행하려다 걸렸는지)는 커밋 메시지에 없어 알 수 없습니다.

## 오늘의 한 줄 정리

- 허용 목록(샌드박스)과 차단 목록(deny 규칙)은 같은 결과를 내도 다른 장치다. 둘이 겹치면 하나는 덜어내도 된다.
- deny 규칙은 글자 모양만 본다. 너무 좁으면 우회한 호출을 놓치고, 너무 넓으면 무관한 명령까지 막는다.
- 이름이 비슷하다고 위험도 같은 건 아니다. `--force` 와 `--force-with-lease` 처럼 동작의 조건을 봐야 한다.
