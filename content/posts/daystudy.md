클로드 코드와 함께 블로그를 두 번 만들었습니다. 코드는 클로드가 거의 다 썼지만, 옆에서 지켜보면서 "이건 왜 이렇게 하지?"를 계속 물었더니 웹이 돌아가는 방식이 조금씩 보이기 시작했습니다. 오늘은 그걸 제 말로 정리해 봅니다.

## HTML, CSS, JavaScript는 각각 무슨 일을 하나

웹페이지 하나는 세 가지 파일이 역할을 나눠 맡습니다. 집에 비유하면 이렇습니다.

- **HTML은 뼈대**입니다. 여기는 제목, 여기는 본문, 여기는 버튼 — 무엇이 어디에 있는지를 정합니다. 이 블로그의 `index.html`이 그 역할입니다.
- **CSS는 인테리어**입니다. 글자 크기, 색, 여백, 다크 모드 — 어떻게 보일지를 정합니다. `style.css` 한 파일이 사이트 전체의 생김새를 책임집니다.
- **JavaScript는 움직임**입니다. 버튼을 누르면 무슨 일이 일어날지, 파일을 언제 가져올지 — 동작을 정합니다. `app.js`, `markdown.js`, `theme.js`가 여기 해당합니다.

셋 중 하나만 있어도 페이지는 뜹니다. HTML만 있으면 꾸밈없는 글이 나오고, CSS까지 있으면 예뻐지고, JavaScript까지 있으면 움직입니다. 그래서 순서도 보통 이렇게 배웁니다.

> 처음엔 세 개가 왜 따로 있는지 몰랐습니다. 지금은 반대로, 하나에 다 넣으면 얼마나 헷갈릴지 상상이 됩니다.

## 마크다운 파일과 파서

### 마크다운은 "쓰기 편한 약속"

HTML로 글을 쓰면 문단 하나에도 `<p>`와 `</p>`를 붙여야 합니다. 제목은 `<h2>`, 굵게는 `<strong>`. 글 쓰는 사람에게는 너무 시끄럽습니다.

마크다운은 그걸 기호 몇 개로 줄인 약속입니다. `#`을 붙이면 제목, `**`로 감싸면 굵게, `-`로 시작하면 목록. 메모장에서도 읽히고, 쓰는 데 방해가 안 됩니다.

```md
## 제목
이건 **굵게**, 이건 `코드`.
- 목록 하나
- 목록 둘
```

### 파서는 "약속을 HTML로 번역하는 프로그램"

그런데 브라우저는 마크다운을 모릅니다. 브라우저가 아는 건 HTML뿐입니다. 그래서 중간에 번역기가 필요하고, 그게 **파서**입니다.

파서는 글을 한 줄씩 읽으면서 "이 줄은 `#`으로 시작하니까 제목이구나" 하고 판단해서 `<h2>제목</h2>`로 바꿔 줍니다. 이 블로그의 `markdown.js`가 그 일을 합니다. 마법이 아니라, 규칙을 하나씩 검사하는 긴 `if`문의 모음에 가깝습니다.

```js
if (line.startsWith('## ')) {
  return '<h2>' + line.slice(3) + '</h2>';
}
```

물론 실제 코드는 이것보다 훨씬 길지만, 하는 일의 본질은 이겁니다. **글자 패턴을 보고 HTML 태그로 갈아 끼우기.**

파서를 직접 만들면서 알게 된 것 하나 — 사용자가 쓴 글에 `<script>` 같은 게 들어 있으면 그대로 HTML에 넣으면 안 됩니다. 반드시 `&lt;script&gt;`처럼 무해한 글자로 바꿔야 합니다. 이걸 빼먹으면 보안 구멍이 됩니다. 라이브러리를 썼다면 몰랐을 이야기입니다.

## "브라우저에서 실시간 변환"이 뭐가 다른가

여기가 첫 번째 블로그와 두 번째 블로그의 가장 큰 차이입니다.

### 첫 번째 방식: 미리 구워 두기

첫 블로그는 컴퓨터에서 스크립트를 한 번 돌려 마크다운을 전부 HTML로 바꾼 뒤, 그 결과물을 올렸습니다. 빵을 미리 구워서 진열해 두는 빵집입니다.

- 장점: 손님(브라우저)은 완성된 빵만 받으면 되니 빠르고, 검색 엔진도 읽기 쉽습니다.
- 단점: 글을 하나 고칠 때마다 오븐(빌드 스크립트)을 다시 돌려야 합니다. 오븐이 고장 나면 빵도 없습니다.

### 두 번째 방식: 주문 받고 굽기

지금 이 블로그는 마크다운 파일을 그대로 올려 두고, 사람이 글을 열 때 브라우저가 파일을 가져와서 **그 자리에서** HTML로 바꿉니다. 주문이 들어오면 굽는 가게입니다.

- 장점: 빌드가 없습니다. `.md` 파일을 저장하면 그게 끝입니다. 구조가 단순해서 어디서 뭐가 일어나는지 다 보입니다.
- 단점: 브라우저가 할 일이 조금 늘고, JavaScript가 꺼진 환경이나 일부 검색 엔진에서는 본문이 안 보일 수 있습니다.

둘 중 뭐가 맞다는 건 아닙니다. 공부용 블로그에서는 "무슨 일이 일어나는지 보이는 것"이 더 중요해서 두 번째를 골랐습니다.

> 같은 마크다운, 같은 결과 화면. 차이는 **번역을 언제, 어디서 하느냐**뿐입니다.

## 프레임워크가 있고 없고

React, Vue, Next.js 같은 걸 프레임워크라고 부릅니다. 이번엔 일부러 안 썼습니다.

### 프레임워크가 해 주는 일

프레임워크는 자주 하는 일을 미리 만들어 둔 도구 상자입니다. 화면 바꾸기, 주소에 따라 페이지 갈아 끼우기, 데이터가 바뀌면 화면 자동으로 갱신하기. 직접 하면 수십 줄인 일이 한두 줄로 끝납니다.

### 안 쓰면 뭘 직접 해야 하나

이 블로그에서 프레임워크 없이 직접 한 일들입니다.

1. 주소가 바뀌면 어떤 화면을 보여줄지 정하기 (`hashchange` 이벤트)
2. 파일 가져오기 (`fetch`)
3. 가져온 내용을 화면에 끼워 넣기 (`innerHTML`, `<template>`)
4. 다크 모드가 첫 화면에서 깜빡이지 않게 순서 맞추기

하나하나는 별것 아닌데, 프레임워크를 쓸 땐 이게 있는 줄도 몰랐습니다. 직접 해 보니 "아, 프레임워크가 이걸 대신 해 주고 있었구나"가 됩니다.

### 그래서 뭐가 나은가

- 실무에서 빨리, 크게 만들어야 하면 **프레임워크**가 맞습니다. 바퀴를 다시 발명할 이유가 없습니다.
- 밑에서 무슨 일이 일어나는지 알고 싶으면 **없이 한 번** 해 보는 게 맞습니다. 그래야 나중에 프레임워크를 쓸 때도 무엇을 대신해 주는지 알고 씁니다.

프레임워크는 지름길입니다. 지름길은 원래 길을 한 번 걸어 본 사람에게 더 값집니다.

## 오늘의 한 줄 정리

- HTML은 뼈대, CSS는 생김새, JavaScript는 움직임.
- 마크다운은 쓰기 편한 약속, 파서는 그 약속을 HTML로 번역하는 프로그램.
- 미리 변환하면 빠르고, 실시간 변환하면 단순하다. 차이는 번역 시점.
- 프레임워크는 편한 도구, 없이 해 보면 도구가 뭘 해 주는지 알게 된다.

다음엔 파서에 표와 중첩 목록을 추가하면서, 정규식이라는 걸 조금 더 파 볼 생각입니다.
