오늘은 블로그 글 자체보다 블로그를 "만드는 방식"이 바뀌었습니다. 미니 웹앱(스도쿠, 포모도로 타이머) 두 개를 새로 넣으면서, 계획부터 배포까지 사람 한 명이 쭉 하지 않고 서브에이전트 여러 개에게 역할을 나눠 맡기는 방식을 처음 써 봤습니다. 커밋 메시지에 "서브에이전트 셋으로 돌렸다"는 말이 반복해서 나오길래, 그게 왜 필요한지 정리해 봅니다.

## 계획, 구현, 검증을 서로 다른 사람에게 맡기듯이

`CLAUDE.md`에는 이제 이런 작업 순서가 적혀 있습니다.

```md
1. Plan — 서브에이전트를 만들어 계획을 작성한다. spec.md로 저장, 사용자 승인.
2. Build — 서브에이전트를 만들어 구현한다.
3. Review — 별도 서브에이전트를 만들어 검증한다. review.md를 작성.
4. Embed — 블로그 메인 페이지에 카드를 추가한다.
```

그리고 규칙 하나가 따로 못 박혀 있습니다.

> Build 서브에이전트와 Review 서브에이전트는 반드시 분리한다.

처음엔 왜 굳이 나누나 싶었습니다. 코드를 짠 사람이 제일 잘 아는데, 그 사람이 검사까지 하면 되지 않나. 그런데 생각해 보면 이건 축구에서 선수가 자기 경기의 심판을 겸하지 않는 것과 같은 이유입니다. 방금 만든 코드는 만든 사람 눈에 자연스럽게 보입니다. 놓친 게 있어도 "내가 그렇게 짰으니까 맞겠지" 하고 넘어가기 쉽습니다. 실제로 스도쿠는 `review.md` 기준 28개 항목 중 통과, 포모도로는 46개 항목을 검토해 2건을 고쳤다고 커밋에 적혀 있습니다. 구현한 에이전트가 스스로 다 통과라고 적었을 리는 없다는 뜻입니다.

## 폴더 하나 안에 전부 담아 두면 서로 안 건드린다

두 앱은 각각 `apps/sudoku/`, `apps/pomodoro/` 안에 자기 완결로 들어갔습니다. `index.html`, `style.css`, `app.js`, 심지어 `agent/plan.md` 같은 작업 지침 파일까지 그 폴더 안에서 끝납니다. 블로그 본체(`index.html`, `css/`, `js/`, `content/`)는 카드 한 줄을 추가하는 것 말고는 손대지 않았습니다.

이게 왜 중요한가 하면, 서브에이전트에게 "이 폴더만 고쳐"라고 경계를 그어 주면 실수로 다른 기능을 건드릴 일이 없기 때문입니다. 사람이 여러 명이 같이 작업할 때 "이 파일은 내가, 저 파일은 네가" 나누는 것과 똑같습니다. 경계가 폴더로 그어져 있으니 검증도 쉽습니다 — 그 폴더만 열어서 마크다운 파서나 라우터가 멀쩡한지 확인하면 됩니다.

## 값이 아니라 변수를 물려받기

앱이 블로그와 따로 노는 폴더에 있어도, 다크 모드까지 따로 만들면 안 됩니다. 그래서 `apps/pomodoro/style.css`는 블로그의 `:root` 색상 변수 블록을 그대로 복사해 오고, 거기 없는 개념(휴식 색)만 새로 더했습니다.

```css
:root {
  --rest: #2b6f9e;
  --rest-soft: #e6f0f7;
}
[data-theme="dark"] {
  --rest: #6fb3e0;
  --rest-soft: #1a2a36;
}
```

포인트는 색을 숫자로 아무 데나 박아 넣지 않고, 라이트·다크 양쪽에 변수로 정의한 다음 컴포넌트 CSS에서는 `var(--rest)`로만 쓴다는 것입니다. 블로그 팔레트를 나중에 바꾸면 앱도 같이 따라오고, `localStorage`의 `theme` 키도 블로그와 공유해서 토글 한 번이면 앱 iframe까지 같이 어두워집니다. "색은 최소로, 전부 변수로"라는 블로그의 다크 모드 원칙이 앱에도 그대로 이어진 셈입니다.

## 오늘의 한 줄 정리

- Plan·Build·Review를 서로 다른 서브에이전트에게 맡기면, 만든 사람이 자기 코드를 다시 검사하는 문제를 피할 수 있다.
- 작업 범위를 폴더로 그어 주면(`apps/{이름}/`) 서브에이전트가 실수로 다른 기능을 건드릴 일이 없다.
- 다크 모드 색은 컴포넌트마다 새로 정하지 않고, 이미 있는 CSS 변수를 그대로 물려받아야 나중에 한 곳만 고쳐도 전체가 맞는다.

## 확인이 필요한 부분

- `test.html 56/56`, `119/119`, `review.md 46/46(수정 2건)` 같은 수치는 커밋 메시지에 적힌 것을 그대로 옮겼습니다. 실제로 브라우저에서 두 테스트 파일을 열어 지금도 전부 통과하는지는 확인하지 않았습니다.
- Plan → Build → Review → Embed 사이클이 이번 두 앱에서 처음 쓰였는데, 앞으로 나올 웹앱에도 계속 이 방식을 쓸 것인지, 아니면 상황에 따라 사람이 직접 만들 때도 있을지는 커밋만으로는 알 수 없습니다.
- 서브에이전트 세 개(Plan/Build/Review)를 실제로 어떤 순서·대화로 불렀는지(한 세션 안에서인지, 별도 세션인지)는 `apps/*/agent/*.md` 지침 파일에 결과만 남아 있어 과정은 추측입니다.
